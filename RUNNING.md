# Running and deploying

## Running from Visual Studio

Open **`ReStore.sln`**. It contains `API` and `API.Tests`. The React client is a create-react-app
project and is deliberately not in the solution.

**Requires .NET 10**, so Visual Studio 2026. Visual Studio 2022 supports up to .NET 9 and will not load
these projects. If you are stuck on 2022, either use the CLI (`dotnet run --project API`) or retarget
both `.csproj` files to `net8.0` — still LTS, but only until November 2026.

### Option A — one process, everything at localhost:5000

Build the client once, then just F5.

```bash
cd client
npm install
npm run build
xcopy /E /I /Y build ..\API\wwwroot     # Windows
```

Press **F5** on `API`. The whole app is at `http://localhost:5000`, Swagger at `/swagger`. This is the
same arrangement as production, so it is the better way to reproduce a deployment problem.

Repeat the copy after any client change — there is no hot reload this way.

### Option B — two processes, with hot reload (normal development)

1. Press **F5** on `API` (or Ctrl+F5 to skip the debugger). It listens on `http://localhost:5000`.
2. In a terminal: `cd client && npm start` → `http://localhost:3000`.

The dev server proxies `/api` to port 5000, so the client uses the same relative URL it uses in
production and no CORS is involved. Edit React files and the browser reloads itself.

To debug both at once, run the API from Visual Studio and the client from VS Code.

### Which launch profile

`API` has two, and they differ only in where the browser opens:

- **http** — opens Swagger. Use it when working on the API.
- **API and client (single site)** — opens the app root. Use it with Option A.

### First-run notes

- **Chromium.** PDF rendering launches a browser. `Reporting:Chromium:ExecutablePath` is empty by
  default and the app finds Chrome, Edge or Chromium automatically — Edge ships with Windows, so this
  works out of the box. Set the path explicitly if you want a specific browser. Only if nothing is found
  does PuppeteerSharp download its own copy, which is slow the first time and needs internet access.
- **Database.** SQLite (`API/store.db`), created and seeded on first run with two demo reports. Nothing
  to install, and no Oracle instance needed.
- **Tests.** Test Explorer, or `dotnet test`. The tests that need a browser skip themselves rather than
  fail if none is found.

# Deploying to IIS

One IIS site serves both the API and the React client. The API hosts the built client from its own
`wwwroot`, so the browser calls a relative `/api` on the same origin.

That choice removes two things you would otherwise have to configure:

- **No CORS.** Same origin, so there is no allowed-origins list to maintain per environment.
- **No IIS URL Rewrite module.** React Router deep links such as `/reports/design/1` are handled by an
  ASP.NET Core fallback route, not by an IIS rewrite rule.

**Not verified on IIS.** Everything here was developed and tested on Linux with Kestrel. The routing is
identical behind the ASP.NET Core Module, and the SPA fallback has integration tests
(`API.Tests/Reporting/SpaHostingTests.cs`), but the IIS specifics below — app pool identity, the
Chromium permissions in particular — need one pass on a Windows box.

## Prerequisites

| | |
|---|---|
| **.NET 10 Hosting Bundle** | Installs the runtime and the ASP.NET Core Module. Not the SDK — the Hosting Bundle. Restart IIS afterwards (`net stop was /y && net start w3svc`). |
| **Node 18+** | Only on the machine that *publishes*, to build the client. Not needed on the server. |
| **Chrome or Chromium** | On the **server**. PDF generation launches it as a child process. |

## Publish

```bash
dotnet publish API/API.csproj -c Release -o ./publish
```

The `BuildReactClient` target runs `npm ci && npm run build` in `client/` and copies the output into
`wwwroot`, so `publish/wwwroot/index.html` and the hashed assets end up in the output. Confirm they are
there before copying to the server.

Publishing the API alone, without a UI:

```bash
dotnet publish API/API.csproj -c Release -o ./publish -p:BuildClient=false
```

If npm is missing the publish still succeeds, with a warning, and produces an API that serves no UI. The
app logs that at startup too rather than failing — `wwwroot` without an `index.html` simply means the SPA
routes are not mapped.

## IIS setup

1. Copy the publish output to the server, e.g. `C:\inetpub\ReStore`.
2. Create an application pool: **.NET CLR version = No Managed Code** (the ASP.NET Core Module hosts the
   runtime; the CLR setting is for classic ASP.NET and must be off).
3. Create the site pointing at that folder, using the pool.
4. `web.config` is generated by `dotnet publish` — do not hand-write one.

## Configuration

Set these in `appsettings.Production.json` on the server, or as environment variables.

```jsonc
{
  "ConnectionStrings": { "DefaultConnection": "..." },
  "Reporting": {
    "Database": { "Provider": "Oracle" },
    "Oracle": {
      "ConnectionString": "User Id=...;Password=...;Data Source=...",
      "PackageName": "PKG_REPORTS",
      "ProcedureName": "GET_DATA"
    },
    "Chromium": {
      "ExecutablePath": "C:\\Program Files\\Google\\Chrome\\Application\\chrome.exe"
    }
  }
}
```

Leave `Cors:AllowedOrigins` unset for single-site hosting. Only set it if you split the client onto its
own site, in which case you also need `REACT_APP_API_URL` set when building the client, because
create-react-app inlines environment variables at build time rather than reading them at run time.

Set `Reporting:Chromium:ExecutablePath` explicitly. If it is empty PuppeteerSharp downloads its own
Chromium on first use, which needs internet access from the server and writes into the app directory —
fine on a developer machine, not what you want in production.

## Chromium under an app pool

This is the part most likely to bite, because PDF generation spawns a browser process and app pools are
deliberately restricted.

- **Execute permission.** The pool identity (`IIS AppPool\<PoolName>` by default) needs read and execute
  on the Chrome binary and its folder.
- **A writable temp directory.** Chromium needs one. Set the pool's **Load User Profile = True**
  (Advanced Settings), otherwise `%TEMP%` may not resolve for the identity and the launch fails with an
  unhelpful error.
- **Idle Time-out = 0** on a reporting server. The default shuts the pool down after 20 idle minutes; the
  browser goes with it and the next report pays the launch cost. The service relaunches Chromium if it
  finds it gone, so this is latency rather than failure.
- **Concurrency.** `Reporting:Chromium:MaxConcurrentRenders` (default 4) caps simultaneous pages. Each
  open page is real browser memory; raise it only with the app pool's memory limits in mind.

If PDFs fail while the rest of the API works, this section is where to look first. The API logs the
Chromium path it launches from at startup.

## Checks after deploying

| Request | Expected |
|---|---|
| `/` | The React app loads |
| `/reports` | Report list, and a hard refresh on this URL still works — that is the SPA fallback |
| `/api/report-templates` | JSON |
| `/api/no-such-endpoint` | **404**, not the SPA shell |
| `/swagger` | Swagger UI, in Development only |
| Generate any report | A PDF — this is the Chromium check |

A blank page with MIME-type errors in the browser console means static assets are being served the SPA
shell instead of themselves. That is a middleware-ordering fault: `UseStaticFiles` must run before
`UseRouting`, because static file serving stands down once routing has matched an endpoint and the SPA
fallback matches everything.
